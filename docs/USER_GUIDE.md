# GlassWire — User Guide

A step-by-step guide to moving a file from an air-gapped screen to a phone. For the frame format
see [PROTOCOL.md](PROTOCOL.md); for how it is built see [ARCHITECTURE.md](ARCHITECTURE.md).

---

## 1. The two files

| File | Where it runs | What it needs |
|---|---|---|
| `dist/sender.html` | the isolated machine | any browser — Chrome, Edge, Firefox, Safari; no network |
| `dist/receiver.html` | the phone | any phone browser; no network |

Both are generated by `python3 build.py` from the readable sources and are committed, so you can
download them straight from the repository. Copy `sender.html` to the isolated side by whatever
route your policy allows (it is ~35 KB). Copy `receiver.html` to the phone, or host it anywhere
over HTTPS — see [Hosting the receiver](#5-hosting-the-receiver).

A headless isolated host (no browser) uses `sender/qr_send.py` instead — see
[Terminal sender](#3-terminal-sender).

## 2. Browser sender

Open `sender.html`. The left panel is the controls, the right is the stage.

1. **Payload.** Click or drop a file onto the drop zone, or type into *…or paste text* (sent as
   `payload.txt`). The stats panel shows the file size, SHA-256, chunk size, frames per loop,
   loop time and goodput for the current settings.
2. **Error correction.** `L` (7 %) is densest and the default. Move to `M` if the camera struggles
   with glare or moiré; `Q`/`H` rarely help on screens.
3. **QR version** sets density: more modules per code, more bytes per frame, but the camera must
   resolve smaller squares. Start at 12. A good phone on a laptop screen handles 15–20; a terminal
   rendering is best at 8–12.
4. **Frame rate.** Start at 6 fps. Phones with a native barcode detector read 10–20 frames/s;
   the embedded decoder reads ~5–10. Keep the sender below the receiver's *scans/s* badge.
5. **Header every N frames.** The header frame (filename, size, hash) is repeated every N data
   frames so a phone can join mid-loop. 8 is a good default; larger means less overhead.
6. **Start.** The codes animate. **Pause**, **Stop**, `space`, `←`/`→` (step one frame) and `f`
   (fullscreen the stage) are available. The sender loops until stopped.

The session id in the caption changes each time a new file is chosen; the receiver uses it to
ignore frames from a previous transfer that may still be on another screen.

### Screen tips

- Fullscreen the stage (`f`) and raise the screen brightness. Turn off night-light / colour
  filters.
- Matte screens photograph better than glossy ones. Angle the screen to avoid reflections of
  ceiling lights.
- Larger on screen is better than denser: prefer a bigger QR version only once the phone decodes
  the current one reliably.

## 3. Terminal sender

For hosts with no browser — servers, appliances, an SSH console:

```bash
python3 sender/qr_send.py FILE --terminal [--fps 4] [--version 10] [--ecl L] [--invert]
python3 sender/qr_send.py FILE --html player.html      # standalone HTML player (open in any browser)
python3 sender/qr_send.py FILE --pbm frames/           # one PBM image per frame, play as a slideshow
echo "text" | python3 sender/qr_send.py - --terminal   # stdin
```

`--terminal` draws each code with Unicode half-block characters (two modules per text row). Make the
terminal window large, use a clean monospace font with no line spacing, and a dark background
with light text (the default renders light-on-dark; `--invert` flips it for light terminals). QR
decoders accept either polarity. Over SSH, latency limits the usable frame rate; 3–4 fps is
realistic.

`qr_send.py` needs only the Python standard library and produces frames bit-identical to the
browser sender.

## 4. Receiver

Open `receiver.html` on the phone. The header shows which decoder is active:

- **native + embedded fallback** — the browser has a native QR detector (Android Chrome, recent
  iOS Safari); it is used for speed and the embedded decoder takes over if it fails.
- **embedded (no dependencies)** — the page's own decoder does all the work.

There are three ways to get frames in.

### Live camera

Tap **Start camera**. Grant camera permission. A torch button appears on phones that have one;
a zoom slider appears where the camera supports it. The green reticle flashes on every decoded
frame and the badge shows scans per second.

The live camera needs a *secure context*: the page served over HTTPS, or opened as a local file in
a browser that treats local files as secure (Android Chrome does). If the button reports that the
camera is unavailable, use the next mode — it needs no permission at all.

### Record, then pick

1. With the phone's normal camera app, film the sender screen for at least one full loop (the
   sender's *loop time* stat tells you how long). Keep the code filling most of the frame.
2. Back in the receiver, tap **Record / pick a video** and choose the clip. On most phones that
   button can also open the camera directly.
3. The clip plays back in the preview while every frame is decoded on the phone. Progress is kept
   across clips, so if chunks are still missing at the end, film another loop and pick it again.

This mode works from a plain local file, with no HTTPS and no network.

### Photos

**Pick photos** decodes still images — useful for very small payloads (one or two frames) or when
you have screenshots from another source.

### Progress and completion

The **Transfer** card shows the session id, chunks received / total, the indices still missing, the
file name, size and expected hash from the header, and a chunk grid (amber = received). When every
chunk is in:

- the hash is computed and compared with the header; **received sha-256** turns green on a match,
  red on a mismatch (press **Reset** and scan again);
- the camera stops;
- **Share…** opens the phone's share sheet with the file attached — pick mail, messaging, a cloud
  drive, AirDrop, Files, anything installed;
- **Save to phone** writes the file to Downloads (Android) or the Files app (iOS);
- **Copy as text** appears for small text payloads.

**Reset** clears the current session; the receiver also resets itself automatically when it sees a
frame with a new session id.

### Optional: forward to an HTTP endpoint

Folded away under *Optional: forward to an HTTP endpoint*. Enter a URL (and a bearer token if the
endpoint wants one) and tap **Upload file**: the raw bytes are POSTed with `X-Filename` and
`X-SHA256` headers. `server/receive_server.py` accepts exactly this and re-verifies the hash. This
is for lab and demo setups; the share sheet is the normal route.

## 5. Hosting the receiver

Hosting is only needed for the live camera on platforms that refuse local files, and for the
home-screen install. The page itself talks to nothing.

| Option | Steps |
|---|---|
| **GitHub Pages** | Put the four files from `dist/app/` in a repo → Settings → Pages → deploy from branch. Open `https://<you>.github.io/<repo>/` on the phone. |
| **Netlify / Cloudflare Pages** | Drag `dist/app/` onto their dashboard. |
| **Your own machine on the same Wi-Fi** | `python3 server/receive_server.py --tls` serves the app at `https://<lan-ip>:8443/` with a self-signed certificate. Accept the warning once. (The home-screen install prompt needs a trusted certificate, so use one of the options above for that.) |

**Install as an app.** Served over HTTPS, Android Chrome shows an *Install as app* button (or ⋮ →
*Add to Home screen*); on iPhone use Share ▢↑ → *Add to Home Screen*. The installed app opens
full-screen and the service worker keeps it working with no connectivity.

## 6. Platform notes

| Platform | Local `receiver.html` | Hosted over HTTPS |
|---|---|---|
| Android — Chrome, Edge, Samsung Internet | Live camera works; Share… works | Everything; installable |
| Android — Firefox | Record-then-pick works; live camera may need HTTPS | Everything |
| iPhone / iPad — Safari | Stock Files app previews HTML without running scripts, so a local copy does not work | Everything; add to Home Screen, then works offline |
| Desktop browser (for testing) | Record-then-pick and photos work; webcam needs HTTPS or `localhost` | Everything |

## 7. Tuning throughput

Goodput is simply *chunk bytes × frames per second*, minus the header overhead. Three knobs:

- **QR version** — the biggest lever. Each step up adds roughly 25–60 bytes per frame. Go up
  until the phone starts missing frames, then back off one.
- **Frame rate** — raise it until *frames/s decoded* on the receiver stops keeping up. Phones with
  the native detector sustain 10–15 fps on v12 codes; the embedded decoder about half that.
- **Compression** — `gzip` or `zip` the file first. JSON and HTML reports shrink 5–10×, which is
  worth more than any decoder tuning.

For reference, a 60 KB HTML report gzips to roughly 12 KB, which at the default settings
is about 50 frames — under 10 seconds per loop.

## 8. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| *scans/s* is high but nothing decodes | Code too dense for the camera distance | Lower the QR version; move the phone closer; fullscreen the sender |
| Decodes, then stalls at a few missing chunks | Those frames land on a moiré/glare spot or the sender is faster than the phone | Lower fps; change the angle slightly; wait for the next loop |
| Hash mismatch | Frames from two different transfers mixed (same session id is impossible, so this is rare) or a corrupted chunk slipped through a decoder | Reset and rescan; use EC level M |
| "Camera unavailable" | Page not in a secure context, or permission denied | Use Record / pick a video; or host over HTTPS |
| Share… is disabled | Browser cannot share files (older Android WebView, desktop) | Save to phone, then share from Files / Downloads |
| Terminal codes won't decode | Font has line spacing or the window is too small | Set line height to 1.0, enlarge the window, use `--version 8`, try `--invert` |
| Upload fails with a network error | Mixed content (HTTP endpoint from an HTTPS page) or an untrusted self-signed certificate | Open the endpoint URL once in the phone browser and accept the certificate; use HTTPS for both |
